Summaryread this and you have the gist

What you must build: a laboratory for ways of reading crypto prices. The user switches on a few analysis methods, the system combines them into many candidate strategies, tries each one against past data, scores them, and ranks which combination did best - then keeps looping to find better ones.

What actually gets graded: not which strategy earns the most, but how many places in the code you have to touch when a new analysis method is added. One new file and it runs = good architecture. Six places to edit = bad architecture.

Size of the job: 11 required modules across four areas - fetch data and draw charts, produce signals and combine them, run experiments and score them, gather news and run machine learning. Plus an architecture document and ADRs.

FATAL MISREADINGThis is not an investing project

Sections 39 and 47 say it outright: the brief does not ask you to prove MA + RSI makes money. It asks for a system where MA + RSI exist today and SMC, Wyckoff or Sentiment can be plugged in tomorrow without the old architecture breaking. Any team pouring effort into tuning indicators for higher returns is aiming away from the marking scheme.

Block 0 // Understanding the problemsections 1-3, 39, 47

Gist: crypto prices run 24/7 and get packaged into candles. Each analysis method only works in one kind of market, so the brief asks: can you build a system that combines several methods automatically and finds the best combination on its own?

What one candle holds

BTCUSDT on the 5-minute timeframe at 09:00 - this is the raw data the whole system rests on:

FieldMeaningExample
Openprice at the start of the 5 minutes118,000
Highhighest price in the 5 minutes118,200
Lowlowest price in the 5 minutes117,900
Closeprice at the end of the 5 minutes118,150
Volumeamount traded in the 5 minutes125 BTC
Why several methods must be combinedthe reason this project exists

Because no single method is right in every market condition:

MethodGood whenWeak when
MAthe market is trending clearlythe market moves sideways
RSIspotting overbought / oversoldmany false signals in a strong trend
Support / Resistancefinding significant price zonesdepends on how you detect the zones

=> if one method can cover another's blind spot, and you have a measuring device to tell which pairing is better, that is where the value of the system lies.

The project is six things stacked togethersection 47

Realtime System | Plugin Architecture | Data Pipeline | Event-driven Architecture | Experiment Platform | Verification Loop.

The system has to turn the sentence "I have a new strategy" into an automatic pipeline: plug in → combine → backtest → score → compare → leaderboard → draw on the chart. And be able to repeat that loop.

Module 1 // Realtime Market Datasection 4

Required path: Binance → Market Data Adapter → Event/Stream → Backend → WebSocket → Frontend.

CONSTRAINTThe frontend must not know Binance exists

Frontend → Binance API is forbidden. It must be Frontend → Market Data Service → Binance Adapter → Binance. That way an OKXAdapter, BybitAdapter or CoinbaseAdapter can be added tomorrow without the frontend changing a single line. This is question 3 in the marking list.

Also forbidden: the frontend calling GET /price over and over to get fresh prices - the server must push, the client must not poll.

Block 2 // Strategy - the heart of the system3 modules - sections 6-14

Gist: every analysis method is forced to speak one language (BUY / SELL / HOLD), plugs into the system with one line of registration, and can be combined with others into a composite.

Module 3 // Strategy Engine - normalising the signalsections 6-11

Gist: a strategy takes market context and returns exactly one of three signals. That is all. Because of that shared shape, everything downstream - combining, backtesting, scoring - never needs to know whether the strategy inside is MA or Wyckoff.

analyze(context) → BUY | SELL | HOLD (or LONG | SHORT | NONE)

context may hold: price, volume, candles, timeframe, indicators, market state, sentiment...

The 4 sample strategies and their parameters
StrategyExample ruleTunable parameters
MA s.7MA20 crosses above MA50 → BUY; crosses below → SELLfastPeriod, slowPeriod
RSI s.8RSI < 30 → BUY; RSI > 70 → SELLperiod, buyThreshold, sellThreshold
Bollinger s.9price below the lower band → BUY, or breaking the upper band → BUYperiod, number of standard deviations
Support / Resistance s.10price near support → BUY, or breaking resistance → BUYthe zone-detection algorithm
KEY IDEAAn indicator is not a strategy

The same Bollinger Bands produce two opposite strategies: buy when price drops below the lower band (mean reversion), or buy when price breaks the upper band (breakout). So a strategy is a trading rule, not an indicator calculation. Separating the two is a real architectural decision.

FORBIDDENA strategy must stay clean

MAStrategy contains MA logic only. Inside it there must be no code that calls Binance, writes to a database, draws a chart, or sends a notification. See also the anti-pattern "Strategy reaches straight into the database" in Block 10.

SMC / Wyckoff (section 11): you are not required to implement them fully. You only have to show the architecture can carry them - adding a new strategy must not require rewriting the Strategy Engine.

Module 4 // Strategy Plugin - add without editingsection 12

Gist: adding a new strategy should ideally be one line: register(SupportResistance).

AStrategyRegistry.register(X) - the engine does not know in advance how many strategies exist. This is what the brief is aiming at.
Bif strategy == MA ... else if == RSI ... else if == BB ... - every addition edits the if-chain. The brief calls this an anti-pattern outright.

Patterns worth researching: Strategy Pattern, Plugin Architecture, Factory, Registry, Dependency Injection.

The brief does not require any specific pattern. What it does require is an answer to: why can your architecture take a new strategy with minimal impact on existing code?

Module 5 // Composite Strategy - combining signalssections 13-14

Gist: combine n strategies and sooner or later they will disagree. The central question of this block: when MA says buy and RSI says sell, what does the system decide?

MethodPrincipleWeakness
Majority Votecount votes, the larger side winsevery strategy counts the same
Weighted Scoreeach strategy gets a weight, sum and compare against thresholdsyou have to pick the weights and thresholds yourself
The weighted-score example from the brief

Encode BUY = +1, HOLD = 0, SELL = -1. Weights MA 0.2 / RSI 0.3 / SR 0.5.

StrategySignalWeightContribution
MABUY0.2+0.2
RSISELL0.3-0.3
SRBUY0.5+0.5
Total0.4

Thresholds: > 0.3 → BUY, < -0.3 → SELL, otherwise HOLD. So 0.4 → BUY.

The brief states plainly that this is only an example - your team may design its own combination method, as long as you can explain it.

Block 3 // Searching combinationsmodule 6 - sections 15-18

Gist: there are far too many possible combinations to try by hand, so you need a machine that generates candidates for you.

Four strategies alone already give 11 combinations. Multiply that by parameter sets (MA 10/20, 20/50, 50/200; RSI 14/30/70, 14/20/80, 21/30/70...) and the search space explodes.

Method 1 // Random Searchrequired for the MVP - section 16

Pick a random combination and push it through the pipeline: generate → backtest → evaluate → rank. Repeat. The simplest option, and enough to pass the MVP.

Method 2 // Domain-guided Searchrecommended - section 17

Instead of pure randomness, use domain knowledge so only meaningful combinations get generated. Group strategies by function:

GroupAnswers the questionMembers
Trendis there a trend right now?MA, MACD
Momentumis the move strong or weak?RSI, Stochastic
Volatilityis the range wide or narrow?Bollinger, ATR
Structurewhere is price sitting?Support/Resistance, SMC, Wyckoff
Informationwhat is happening off the chart?News Sentiment

Then set a rule, for example: a composite must contain 1 Trend + 1 Momentum + 1 Structure. That way the system produces MA + RSI + SR instead of MA10 + MA20 + MA50 - those last three all say the same thing, so combining them is pointless.

The brief demands an explanation: how was domain knowledge fed into the search?

Method 3 // Advancednot required - section 18

Genetic Algorithm, Bayesian Optimization, Evolutionary Search, Reinforcement Learning, LLM-generated Strategy, Agent-based Search, AlphaEvolve-style optimization, Loop Engineering.

ARCHITECTURE POINTSearch must unplug like a plug

Define interface StrategyGenerator { generate() } with several implementations (Random / DomainGuided / Genetic). Everything downstream only receives a CandidateStrategy and never needs to know how it was produced. This is exactly the scenario in section 42 that the lecturer may ask you to perform on the spot.

Block 4 // Backtest and scoring2 modules - sections 19-22

Gist: run a candidate over past data, count each winning and losing trade, then reduce that to a few numbers so candidates can be compared.

Module 7 // Backtesting Enginesection 19

Gist: answers "if I had used this strategy in the past, what would have happened?" - takes a stream of signals, simulates entering and exiting, and outputs a list of trades with their profit and loss.

TradeInOutResult
182K86Kprofit
288K87Kloss
Profit alone is not a verdictsection 20

The brief's example: candidate A returns +30% but was once down -45%; candidate B returns +25% but at its worst was only down -8%. B is steadier despite earning less. So risk has to be measured too.

MetricWhat it measuresMVP
Total Returntotal profit or loss over the periodrequired
Win Rateshare of winning tradesrequired
Max Drawdownhow far it fell at its worstrequired
Number of Tradeshow many times it enteredrequired
Profit Factorgross profit / gross loss
Sharpe Ratioreturn per unit of risk
PRINCIPLEEvaluation is separate from implementation

The brief says you do not need deep quantitative finance, but you must understand this: scoring lives outside strategy code. A strategy only produces signals; it never computes its own profit.

Module 8 // Leaderboardsections 21-22

Gist: a Top-K table (say K = 10). A newly scored candidate only enters the table if it beats whoever currently sits at rank K.

Allow sorting by Return / Win Rate / Max Drawdown / Sharpe, or roll them into one Overall Score, for example 0.5 x Return + 0.2 x WinRate + 0.3 x RiskScore.

The formula is yours to define - but the report must spell out how it is computed.

Block 5 // The continuous loopmodule 9 - sections 23-24

Gist: chain the blocks above into a background loop that generates, tests, scores and ranks by itself - and knows when to stop.

  1. 1
    Generate Strategy
    produce the next candidate (Random or Domain-guided)
  2. 2
    Backtest
    run over historical data → list of trades
  3. 3
    Evaluate
    trades → Return / Win Rate / MDD
  4. 4
    Rank
    metrics → Overall Score
  5. 5
    Leaderboard
    enter the Top-K if the score is good enough, then back to step 1
REQUIREDYou must design a stop condition

The brief forbids an uncontrolled while(true). Design a stopping rule - for example 100 candidates, or one hour, or no improvement after 50 rounds.

Why the loop is an architecture question, not an algorithm questionsection 24

The bad way: one function doing for 100000 strategies { compute indicator; backtest; save DB; update UI } - everything crammed into one place.

The good way: split it into a pipeline with clear boundaries:

Strategy Generator → Strategy Queue → Backtest Worker → Evaluator → Ranking Service → Leaderboard

Once split, things the bad version simply cannot do become natural:

  • [x]run several workers in parallel
  • [x]retry when a worker fails
  • [x]pause and resume the loop
  • [x]watch how far it has got
  • [x]swap the search algorithm without touching the rest
  • [x]scale later
Block 6 // Showing the user what the system didsections 25-26

Gist: showing Profit = +20% is not enough. The user has to see where the strategy bought, where it sold, and why.

Click a candidate on the leaderboard → the chart draws the MA20 line, the RSI signals, the support zones, the buy points and the sell points.

Plus a table of every trade (number, entry time, entry price, exit time, exit price, result %). Click a row → the chart jumps to that trade and highlights its entry and exit.

Block 7 // News and sentiment2 modules - sections 27-30

Gist: price does not depend on the chart alone, so the system collects news, has a machine-learning model read whether it is positive or negative, and then turns that result into... another strategy.

Module 10 // News Crawlersections 27-28

Gist: collect news from several different sources but normalise it into one shape, so swapping a source does not affect anything downstream.

The NewsItem shape: id, title, content, source, publishedAt, crawledAt, relatedCoins, url.

Structure: one News Provider abstraction, with RSS / News API / Crawler underneath it - all three returning the same NewsItem. Wiring Trading System → Website A Crawler directly is forbidden.

Module 11 // Sentiment Analysissections 29-30

Gist: a machine-learning service reads an article, labels it POSITIVE / NEGATIVE / NEUTRAL with a score (for example 0.82), and stores that alongside the article.

THE NICEST IDEA IN THE BRIEFSentiment becomes an ordinary strategy

NewsSentimentStrategy: average sentiment over the last hour > 0.7 → BUY, < -0.7 → SELL. Because it obeys the same analyze(context) → BUY/SELL/HOLD shape, the search engine naturally produces MA + RSI + Sentiment or SR + Sentiment. The architecture is no longer confined to technical analysis - this is the strongest evidence of extensibility your team can take into the demo.

FORBIDDENThe crawler must not call the ML model

Crawler → BERT model is forbidden. The crawler does one job: collect news. The Sentiment Service is where analysis happens. This is anti-pattern number 5 in Block 10, and it is question 6 ("if the sentiment model changes, is the Strategy Engine affected?").

What to build29 tasks // 6 vertical slices

Gist: 29 pieces of work, grouped into 6 vertical slices. Every slice ends in something you can click - not a backend pile followed by a frontend pile.

The Evidence in the brief column quotes the exact passage the task comes from, so during the defence you can point at the brief's own words. Three kinds of tag: no tag = the brief demands it outright; inferred = the brief does not spell it out but skipping it breaks another requirement; not in the brief = the team added it and must justify it. BLOCKING = a decision that shapes an interface or the DB schema, and changing it later means rewriting much of the system; optional = not required.

HOW TO READ THISWhy slice vertically instead of by backend / frontend

Splitting by module fails here, because all 11 modules in the brief are backend modules - the UI gets pushed to the end, there is a long stretch where module after module is finished while the screen stays blank, and every contract mismatch between them lands in the final assembly week, exactly when there is no time left to fix it.

Slicing vertically makes each slice prove itself. Slice 2 is the valuable one: it cuts through Strategy → Backtest → Evaluator → UI the moment those modules are first built, so the contracts between them are tested while they are still cheap to change. Its last two tasks (T15, T16) double as a direct measurement of the very thing being marked: what does adding a strategy cost, and does combining them force changes downstream.

Order within a slice: the backend tasks can run in parallel; the task that closes a slice is the one with a screen - and if a slice will not close, do not open the next one.

FIRST OF ALL10 blocking decisions live in T01, T02, T11, T17

Lock them before the first line of code. T01 and T02 should be done by the whole team in one sitting, not handed to one person - T02 in particular carries two easily-missed decisions: the shape of StrategyContext and the notion of a dataset. See the two explanation blocks under the slice 0 table.

BLOCKINGWhy StrategyContext is locked in T02, not T11

Section 6 says context may hold price, volume, candles, timeframe, indicators, market state and sentiment. Leave T11 to define it around whatever is needed at that moment and it will hold candles + indicators only - the four strategies in T11/T15 still run fine, and it breaks at T25, when NewsSentimentStrategy needs a sentiment score that context has no way to carry. At that point only three exits remain, and all three cost marks: change the Strategy interface, so every existing strategy changes with it - precisely the section 41 scenario being marked; let the strategy query the database itself - straight into the "strategy reaches into the database" anti-pattern of section 44; or build a side channel for sentiment outside the Strategy Engine - losing the best idea in the brief (section 30).

So StrategyContext must be an extensible data gateway - adding a new data source never changes the analyze() signature - rather than a fixed struct.

DECIDE TOGETHERDataset - a team decision, not one person's

Section 33 backtests over BTCUSDT / 01-01 → 01-07 / 5m. That triple - pair + range + timeframe - is the dataset, and it is the Dataset column of the Experiment table in T03. Two consequences follow: every result is stored with its dataset (section 36 - re-runs must match), and the leaderboard may only rank candidates from the same dataset - mixing two date ranges into one table makes the comparison meaningless.

The dataset picker itself is built in T14 and reused in T20; but the concept and its storage must be locked here, because changing it later means changing the schema.
